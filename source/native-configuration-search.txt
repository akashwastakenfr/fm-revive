On the PC platform, different PC's may support different modes based on the configuration of the PC software and hardware. On other console platforms, the modes supported will typically not change.
If the specified output mode is not supported on the given platform/configuration, the next most logical output mode will be notched down to and selected automatically. For most platforms, this means the output mode could always be set to 7.1 if desired and the closest supported mode will be selected. The output mode should ideally be set before the Dac is started. However it can be changed while the Dac is running without any lasting side effects to the EAAudioCore code or game code on PC and PS3. The audio output will be interrupted for a brief period, which can sound disconcerting. If this is an issue the signal on the mastering voice could be faded down and back around the switch by manipulating a fader PlugIn appropriately. For iOS the output mode must be set before the Dac is started.
For Android, the output mode selection is handled via Java code AndroidEAAudioCore.Startup (channels).When a channel configuration with more channels than what the output is set to is fed to the Dac, it will perform an industry standard fold-down to the required configuration (5.1, quad, stereo or mono). Even if the Dac PlugIn is not performing the fold-down, the PC or console platform might be performing a fold-down on its end. Hard clipping can be introduced during the fold-down if the signal coming into the fold-down is loud. Although the hard clipping should not be as audible a problem as it might sound, it can be avoided by reducing the volume of the signal before it goes into the Dac PlugIn. If a signal is normalized to full scale (+/- 1.0) before it enters the Dac PlugIn by a PlugIn such as a compressor, then when folding down to quad or stereo, reducing the signal to approximately 45% (-6.9 dB) of its original level will ensure no hard clipping will occur. On the other hand, hard clipping noise is not as noticeable as one might think. Furthermore, given that it may be quite unlikely that the mix will be driven in game to produce the extreme configuration required to produce the maximum peak (greater than +/- 1.0) after fold-down, it is suggested that users not worry too much about clipping possibilities, especially since the additional reduction of volume to avoid it may result in the game output being too quiet.
The MatrixPanner PlugIn is used to place a mono sound source on multiple speakers, where each speaker has a separate gain controller. The objective is to create a sense of placement relative to the game player when playing sounds. The gain levels should be specified from 0.0 to 1.0. Negative values are allowed to invert the signal. At present, the configurations supported are 1X2, 1X4, 1x6 and 1X8. 
PS4 details: The Object3DOutput PlugIn has been created to leverage the capabilities of Sony's Audio3D library which provides 3D object audio capabilities on the PS4 platform. Each PlugIn instance can be used to represent an audio emitter in 3D space. The object position, gain and other attributes are preserved as metadata and passed along with the mono audio waveform data to the Sony Audio3D library API which will either pass it on to a 3D Object Audio capable receiver or to headphones if connected, or render the audio to a 7.1 mix for output along with the rest of the audio mix. In the case of a 3D Object Audio capable receiver, it is expected that such a receiver would render the object audio based on the speaker configuration it is using, which ideally would include speakers above (and possibly below) the plane in order to experience more accurate 3D sound. In the case of headphones, head-related-transfer-function (HRTF) techniques could be used to render the audio in 3D. Note that the mixer sample rate must be set to the default 48 KHz value (which is the output sample rate of the PS4) because Object3DOutput does not resample the mix to the hardware output rate. Thus the System must be run at the same rate as the hardware in order for the PlugIn to work. For more information on this functionality, please refer to the PS4 Audio3D library documentation.
By default the front speakers are set 30 degrees from front center, the rear speakers are 110 degrees from front center, and the far rears at 150 degrees from front center. This provides a reasonable compromise for operation in quad/5.1 channel cases versus 7.1. If users want a configuration specific to a given output channel configuration, they should set the speaker locations either via calling the aforementioned SetDefaultFront/Rear/FarRearSpeakerAngle() functions, or by using the constructor parameters. For example, users may want a 7.1 channel configuration where the front, rear, and far rear speakers are equidistant. Such an equidistant relationship provides some nice benefits when rotating multi-channel content around in a circle, as it means a stereo image with 60 degree separation can be rotated to emanate from any two speakers without bleeding of the image, assuming the centre level of the panner is set to 0. If the voice outputs 5.1 channels (i.e., the voice containing this panner has 6 output channel rather than 8), then for the same equidistant properties, values of 45 and 135 degrees should be used for the front and rear speaker geometries respectively. 
For all source channel configurations, the front, rear, and far rear source geometry can be adjusted independent of the speaker geometry. By default, the source geometry is the same as the speaker geometry.
For speaker configurations that include a LFE channel, the PlugIn will pass through the incoming LFE channel by ATTRIBUTE_SETLFEPASSTHROUGHLEVEL. ATTRIBUTE_SETLFEPASSTHROUGHLEVEL has no effect if the source is without a LFE channel. The other LFE control, ATTRIBUTE_SETLFELEVEL, scales each source channel and adds to the output LFE, if applicable. 
The Pan3D PlugIn allows for spatializing a mono signal over stereo, quad, 5.1 , or 7.1 channel configurations. The PlugIn is intended for use in conjunction with a higher level 3D audio application such as the EAAudio3D (or EAAudioSimple3D) library. This higher level library is responsible for producing a set of path parameters (delay amounts, azimuths, gains, filter cutoffs, etc.) for a direct path and several indirect paths which are to be used by Pan3D in spatializing the input signal.
The geometry of the panner can be over-ridden once globally in game code by calling EA::Audio::Core::Pan3D::SetDefaultFrontSpeakerAngle(),  EA::Audio::Core::Pan3D::SetDefaultRearSpeakerAngle(), and EA::Audio::Core::Pan3D::SetDefaultFarRearSpeakerAngle(). The geometry can also be over-ridden on a per instance basis by setting the appropriate angle-based constructor parameters of Pan3D.  To help minimize memory fragmentation due to allocations made internally by ReverbIR1, the constructor parameter CONSTRUCTORPARAM_MAXREVERBLENGTH has been provided. Users should set this to the longest impulse response (in seconds) used in their game if they want to minimize memory reallocations. If interested in further minimizing reallocations, users are advised to alternately use reverb slots 0 and 1 as they move from one impulse response file to the next. Not only does this allow cross fading from one to the other via the gain attributes, but it avoids the memory reallocations that would occur if the same slot were used. Specifically, when only a single reverb slot is being used/reused, ReverbIR1 does not insist that a newly applied reverb file be configured identically to the previous one, thereby allowing for a change in configuration if this is required. However, if slots are being alternately used (with some non-zero time overlap), then since this implies they must be configured the same, there does not need to be any memory reallocation (as long as the reverb files are never larger than the largest reverb used thus far and/or the value set in the constructor parameter CONSTRUCTORPARAM_MAXREVERBLENGTH). Also note that an EVENT_STOPREVERB1 event need not be used prior to applying a new reverb file, as the application of the new reverb file will result in the previous one not being accessed further by the ReverbIR1 instance. One reason to apply the stop event would be if there was some time during which only one reverb was needed, especially if the next reverb needed was not yet known. However, as long as slots are alternated and at least one slot is always active, use of the stop event should not cause additional reallocations.
The ReverbIR1 PlugIn supports several channel-impulse response file configurations. 1:1 source to output channel mappings (1, 2, 4, 6 or 8 channels) are supported, where the impulse response file is either mono, or it is comprised of the same number of channels as the signal input. Also, a 1:n source to output channel configuration is supported (1, 2, 4, 6 or 8 output channels), where the impulse response file is comprised of n channels.
A SampleReader instance can output a dynamic number of channels (between 1 and the number of output channels it was created with). It is suggested that the player be followed by a Rechannel PlugIn when dealing with multiple source asset channel configurations on a single player.
A SndPlayer1 instance will output a variable number of channels equal to the number of channels int the source sample data. In order for a single voice to handle assets with differing channel configurations, it will need to be followed by a PlugIn which provides a constant number of channles as output such as Rechannel (for standard fold-up or fold down behaviors) or MapChannels (for simple copy, clear behaviors). For more details on their precise behaviors, please see the documentation those PlugIns. To determine the number of channels in an SndPlayer1 asset at runtime you can use the static member function SndPlayer1::GetFileInfo()
SndPlayer1 is one of the few PlugIns that supports non-standard channel configurations (up to 64). The Route PlugIn can be used to bus selections of channels to SubMix PlugIns, which can be useful for efficiently streaming layers of interactive music or ambience. For example, a stream file could be authored that contains 4 intensities of stereo crowd ambience. The 8 channel SndPlayer1 output can be routed into 4 stereo SubMixes, and then each SubMix Voice can vary its volume appropriately to cross-fade between the 4 intensities. This approach may use more CPU time than other approaches, but streaming a single 64 kilobyte/s stream will be far easier on a DVD than streaming 4 16 kilobyte/s streams. In most cases DVD bandwidth will be far more scarce than CPU bandwidth.
